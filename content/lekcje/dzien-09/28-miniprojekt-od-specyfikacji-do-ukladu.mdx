## Faza 0 — Setup projektu

Załóż nowy projekt PlatformIO: **New Project → Board: Arduino Uno → Framework: Arduino**. Sprawdź `platformio.ini` (`board = uno`, `framework = arduino`, `monitor_speed = 9600`). Jeśli używasz Gita — zrób pierwszy commit, żeby móc cofnąć zmiany, gdyby AI namieszało.

## Faza 1 — Definicja problemu (bez AI)

Najpierw **Ty** opisujesz problem zwykłym językiem: „kierowca cofa; im bliżej przeszkody, tym szybsze piknięcia i zapalona dioda; po przekroczeniu 30 cm — cisza". Możesz poprosić AI **wyłącznie** o wskazanie przypadków brzegowych: „co, gdy czujnik się odłączy?". Odpowiedź zapisujesz jako kilka zdań — to fundament specyfikacji.

## Faza 2 — Specyfikacja, elementy i połączenia (z weryfikacją)

Korzystamy ze specyfikacji napisanej w lekcji o SDD. Teraz dochodzi **lista elementów** i **tabela połączeń** — a każdą deklarację sprzętową **weryfikujemy**.

Najważniejszy moment weryfikacji dotyczy **brzęczyka**. Zadajemy AI celowe pytanie kontrolne:

<Code lang="text" file="prompt-weryfikujacy.txt">
```
Brzęczyk aktywny 5 V pobiera ok. 30 mA, podłączony do pinu D5 Arduino UNO.
Limit ATmega328P to 40 mA absolutnego maksimum (zalecane 20 mA) na pin.
Czy mogę sterować nim wprost z pinu, czy potrzebny tranzystor?
```
</Code>

Dobra odpowiedź wskaże, że **30 mA przekracza zalecane 20 mA**, więc potrzebny jest **tranzystor NPN** sterowany przez pin (z rezystorem 1 kΩ na bazie). Ale — zgodnie z zasadą z lekcji o weryfikacji — potwierdzamy to w **dokumentacji**, nie w czacie. To właśnie tu metoda chroni sprzęt.

## Faza 3 — Symulacja w Wokwi (przed budową)

Zanim sięgniesz po elementy, złóż układ **wirtualnie** w Wokwi i sprawdź wstępny szkielet kodu. Jeśli logika progów albo czas pomiaru są błędne, zobaczysz to bezpiecznie na ekranie. Dopiero symulacja, która działa zgodnie ze specyfikacją, daje zielone światło na sprzęt.

## Faza 4 — Generowanie kodu z AI

Teraz prompt według schematu **Cel–Kontekst–Format** (z lekcji o SDD): podajesz płytkę (Arduino UNO R3 / ATmega328P), styl PlatformIO, **całą specyfikację** i **konstytucję** (millis zamiast delay, brak String, nazwane stałe). Po kilku iteracjach i poprawkach powstaje czysty, nieblokujący szkic:

<Code lang="cpp" file="src/main.cpp">
```cpp
#include <Arduino.h>

// --- Piny ---
const byte PIN_TRIG   = 9;
const byte PIN_ECHO   = 10;
const byte PIN_BUZZER = 5;    // sterowany przez tranzystor NPN
const byte PIN_LED    = 6;

// --- Progi odległości (cm) ---
const int PROG_BLISKO = 10;
const int PROG_DALEKO = 30;

// --- Okresy czasowe (ms) ---
const unsigned long OKRES_POMIARU = 200;
const unsigned long PIK_SZYBKI    = 100;
const unsigned long PIK_WOLNY     = 500;

unsigned long ostatniPomiar = 0;
unsigned long ostatniPik    = 0;
bool buzzerStan = false;
long odleglosc  = 0;

// Pomiar odległości; zwraca cm albo -1 przy braku echa
long zmierzOdleglosc() {
  digitalWrite(PIN_TRIG, LOW);
  delayMicroseconds(2);
  digitalWrite(PIN_TRIG, HIGH);
  delayMicroseconds(10);
  digitalWrite(PIN_TRIG, LOW);

  long czas = pulseIn(PIN_ECHO, HIGH, 25000UL); // limit czasu 25 ms
  if (czas == 0) return -1;                      // brak echa / czujnik odłączony
  return czas / 58;                              // czas [us] -> odległość [cm]
}

// Nieblokujące pikanie brzęczyka z zadanym okresem
void pikaj(unsigned long teraz, unsigned long okres) {
  if (teraz - ostatniPik >= okres) {
    ostatniPik = teraz;
    buzzerStan = !buzzerStan;
    digitalWrite(PIN_BUZZER, buzzerStan);
  }
}

void setup() {
  Serial.begin(9600);
  pinMode(PIN_TRIG, OUTPUT);
  pinMode(PIN_ECHO, INPUT);
  pinMode(PIN_BUZZER, OUTPUT);
  pinMode(PIN_LED, OUTPUT);
}

void loop() {
  unsigned long teraz = millis();

  // Pomiar co OKRES_POMIARU (bez blokowania pętli)
  if (teraz - ostatniPomiar >= OKRES_POMIARU) {
    ostatniPomiar = teraz;
    odleglosc = zmierzOdleglosc();
    Serial.print("Odleglosc: ");
    if (odleglosc < 0) Serial.println("brak echa");
    else { Serial.print(odleglosc); Serial.println(" cm"); }
  }

  // Sygnalizacja na podstawie progów
  if (odleglosc > 0 && odleglosc < PROG_BLISKO) {
    digitalWrite(PIN_LED, HIGH);
    pikaj(teraz, PIK_SZYBKI);
  } else if (odleglosc >= PROG_BLISKO && odleglosc <= PROG_DALEKO) {
    digitalWrite(PIN_LED, LOW);
    pikaj(teraz, PIK_WOLNY);
  } else {
    digitalWrite(PIN_LED, LOW);
    digitalWrite(PIN_BUZZER, LOW);
    buzzerStan = false;
  }
}
```
</Code>

## Faza 5 — Przegląd kodu (bramka)

Zanim wgrasz, przejdź **checklistę z lekcji o weryfikacji**. Dla tego kodu odpowiedzi są dobre: używa `millis()` zamiast `delay()` w pętli, nie ma klasy `String`, stałe są nazwane, jest obsługa braku echa (`-1`), a brzęczyk idzie przez tranzystor (prąd pinu w normie). Gdyby coś nie pasowało — odrzucasz kod i prosisz AI o poprawkę konkretnego punktu.

## Faza 6 — Kompilacja i wgranie

Zbuduj projekt (`pio run`), wgraj (`pio run --target upload`) i otwórz monitor (`pio device monitor`). Jeśli kompilator zgłosi błąd — np. zmyśloną funkcję — to **dobra wiadomość**: złapaliśmy halucynację, zanim trafiła na sprzęt. Skopiuj dokładny komunikat i wklej do AI razem z kodem.

<ExpectedOutput title="Po wgraniu">
W monitorze portu co 200 ms pojawia się odczyt odległości w cm. Po zbliżeniu ręki do czujnika: poniżej 30 cm brzęczyk pika wolno, poniżej 10 cm pika szybko i zapala się dioda, powyżej 30 cm — cisza i zgaszona LED.
</ExpectedOutput>

## Faza 7 — Test

Sprawdź wszystkie progi i przypadki brzegowe ze specyfikacji: odłącz na chwilę czujnik — w monitorze powinno pojawić się „brak echa", a układ nie może „zawiesić" pikania. Porównaj zachowanie z **kryteriami akceptacji** — to one mówią, czy projekt jest gotowy.

## Faza 8 — Debug i rozbudowa

Jeśli coś nie gra, użyj **ustrukturyzowanego promptu debugującego**: opisz objaw, oczekiwane zachowanie, fragment kodu i odczyt z monitora, a poproś AI o „trzy najbardziej prawdopodobne przyczyny i jakie `Serial.print()` dodać". Gdy działa — rozbuduj projekt.

<MiniProject title="Czujnik cofania — pełny przepływ z AI" goal="Od specyfikacji do działającego układu, z weryfikacją na każdym etapie">
Zbuduj i uruchom czujnik cofania, przechodząc wszystkie dziewięć faz. Oddajesz **dwie rzeczy**: (1) swoją **specyfikację** w pliku `.md` oraz (2) **działający, zweryfikowany szkic** w PlatformIO.

Propozycje rozbudowy (wybierz jedną):

- dołóż **trzeci próg** i drugą diodę (np. zielona–żółta–czerwona jak sygnalizacja),

- uśrednij **kilka pomiarów**, żeby odczyt był stabilniejszy,
- przenieś projekt na **robota** z poprzednich zajęć jako czujnik antykolizyjny.

Każdą zmianę najpierw dopisz do **specyfikacji**, dopiero potem proś AI o kod — i znów przejdź przez bramkę przeglądu.

## Podsumowanie

Zbudowaliśmy realny układ, łącząc cały moduł w jeden **powtarzalny przepływ pracy**.

Kluczowe wnioski:

- Każdy projekt z AI prowadzimy przez **9 faz**: od problemu i specyfikacji, przez symulację i przegląd, po test na sprzęcie.
- **Specyfikacja** jest źródłem prawdy, a **weryfikacja** (bramka sprzętu + przegląd kodu) chroni sprzęt.
- **PlatformIO + AI + SDD** to warsztat inżyniera: maszyna pisze kod, człowiek odpowiada za projekt i bezpieczeństwo.
- Efekt projektu to nie tylko działający układ, ale też **specyfikacja** — dokument, który pokazuje Twoje myślenie.

To zamyka moduł o nowoczesnym, wspieranym przez AI programowaniu systemów wbudowanych. Masz teraz komplet narzędzi i — co ważniejsze — **metodę**, która sprawia, że AI Cię wzmacnia, zamiast wyręczać.
